Apple's Object Capture sample runs on the first try. That is the problem.

It runs on a warm device, in a lit room, on a scan nobody cancels, with no product around it. Every one of those conditions is doing work, and none of them survive contact with a shipping app. The gap between "the sample runs" and "a customer measures their own furniture and gets a fitted result back" is where all the engineering is, and almost none of it is 3D.

This is a build guide for that gap. What you have to decide, what the framework will not decide for you, and the specific failures that only show up on a real device in someone's living room.

## First, decide what is native at all

Before any of the 3D, there is a boundary question, and getting it wrong costs more than any API problem in this article.

The commerce experience — catalogue, basket, prices, promotions — is a website with a team shipping to it continuously. None of that belongs in an iOS release cycle. The measurement is native: it needs LiDAR, a photogrammetry pipeline and a camera session, and no browser can reach any of it.

So the product is a web page that, at one moment, needs a native capability and then needs the answer back. Native capture is presented *over* the page, full screen, not instead of it — the page stays loaded underneath, which means there is always a back and no navigation state to rebuild when the scan ends.

Everything downstream follows from that one sentence. Decide it first, write it down, and defend it — because every field the app learns to understand is a field the web team can no longer change alone.

> **Decide which side of the boundary owns the product before you write a line of capture code.** The capture is a feature. The boundary is the architecture.

## Two sessions, not one

The single most useful thing to know before you start: scanning an object on iOS is **two** RealityKit sessions with a directory between them.

[`ObjectCaptureSession`](https://developer.apple.com/documentation/realitykit/objectcapturesession) runs the camera and the LiDAR sensor. It guides the user around the object and writes HEIC images into a directory you hand it, plus a checkpoint directory for its own intermediate state. It does not produce a model.

[`PhotogrammetrySession`](https://developer.apple.com/documentation/realitykit/photogrammetrysession) takes that images directory — not the checkpoint directory — and reconstructs a textured USDZ from it, on device, with the camera long since shut down.

They are separate types, they run at different times, and they are gated separately:

```swift
let captureSupported = ObjectCaptureSession.isSupported
let reconstructionSupported = PhotogrammetrySession.isSupported
```

**A device can pass the first and fail the second.** Some iPads do exactly that. Check only the capture half and you let a customer spend two minutes orbiting a chair before failing them at the one point in the flow where their work is already done and cannot be moved to another device.

So the capability check answers both halves plus camera permission, up front, before anything is constructed — and the landing screen calls the *same* check the engine calls, rather than reimplementing it. A landing screen that promises a scan the engine will then refuse is worse than no landing screen.

One honesty note, because it is easy to overclaim: **there is no LiDAR query in any of this.** `ObjectCaptureSession.isSupported` is the only authoritative gate Apple publishes. "Requires LiDAR" is a label you put on it returning false. It happens to be true today — the floor is a LiDAR device on an A14 or newer — but you are reporting Apple's opinion, not a sensor's.

> **Check every gate the pipeline depends on before the user does the expensive part.** The one you forgot is the one that fails after the work cannot be repeated.

## The configuration is trivial. Everything around it is not.

The entire capture setup is two properties: a checkpoint directory, and whether over-capture is enabled. That is the whole surface, and it is exactly why the sample runs first try.

Two things around that call cost real time before they were understood, and neither is discoverable by reading the API.

**The directories have to exist, every single time.** The session does not create them and does not retry. Worse, a missing *checkpoint* directory does not fail at start — it fails later, cascading, on the second scan pass, when checkpoints are first written. A retention sweep, a manual cleanup, or a sync between creating the session record and starting capture is enough to remove them. Create them idempotently immediately before starting, and a failure that otherwise looks like a bug in your scan-pass handling disappears.

**The first state has to be read by hand.** The state stream only emits on *changes*. A session that begins in `.initializing` and stays there — which it does when the depth pipeline cannot get valid points — emits nothing at all. Observe only the stream and your app sits on a loading screen forever, in precisely the situation where the user most needs to see the camera.

## Own the state machine

Apple's capture state has seven cases. Your app needs more than seven, and it needs one of them to mean something slightly different.

<CaptureStateMap />

Most of the mapping is one-to-one and boring. The first row is neither.

Mapping `.initializing` onto *ready* is a deliberate lie, and it is the right one. ARKit already feeds the camera preview while the depth pipeline warms, so rendering the camera at that point means the user can aim. Leave it honest and you ask someone to point their phone at an object on a screen that shows them nothing. Apple emits a genuine ready shortly after; it maps to the same value, so the duplicate transition is a no-op and nothing flickers.

The other half of that discipline is what you do with a case you have never seen. An unknown future state should make your app *ignore an update* — not invent a transition it has never been tested against. Same for feedback signals and errors: give every mapper an explicit unknown slot so a case Apple adds next year surfaces as "something we do not handle" instead of falling off the end of a switch.

There is a broader reason to own this layer rather than observe Apple's types directly. In iOS 17 beta 4, `ObjectCaptureSession` silently moved from Combine's `ObservableObject` to the Observation framework. Any view bound straight to the session broke. A thin type of your own in between turns that into an internal change.

> **Never let a framework type appear in your own public signatures.** A rename upstream should be a patch release for you, not a migration.

### The count that does not count

The capturing state carries an image count. It is frozen at zero.

The state stream fires on *state* changes. A user orbiting an object for forty seconds stays in capturing the whole time — one emission, and whatever the payload said on entry is what it says forty shots later. Bind a UI counter to it and the user watches the camera take photographs while the number sits still.

The live figure is `numberOfShotsTaken`, read on demand rather than pushed.

That matters beyond a label. Most apps also watch the images directory to drive progress — and a directory watcher built on `DispatchSource` **coalesces events and misses bursts**, so a genuine thirty-shot scan can look like twelve. Two counters for one quantity is not sloppiness if you are deliberate about it: the watcher is what makes progress visible, and the session's own count is what makes a decision correct. Reconcile them at the decision point, and only there.

> **Know which of your numbers is authoritative.** A display value and a decision value are allowed to be different things — as long as you know which is which.

### Feedback is a set, and sets need diffing

The feedback stream publishes the set of conditions currently true — too far, too close, too dark, moving too fast, out of frame, and five more. It is level-triggered: the same set arrives again and again while nothing changes. Drive a UI straight off it and every badge re-animates on every emission.

Diff it against the previous set and you get events — appeared, cleared — which is what a UI actually wants.

One field note that will save you an afternoon: in a badly lit room the session emits low-light and moving-too-fast feedback while the console fills with `No depth map is available in ARFrame!`, `Invalid input pointcloud` and `No points with valid confidence`. Those are descriptions of the room, not defects in your code. Check the light before you read the stack trace.

## Guidance is the part you actually design

This is where the framework stops and the product starts, and it is much larger than it looks.

The API hands you three actions — begin another orbit, begin an orbit after the user flips the object, finish — and one signal that says the user completed a sweep. It has no opinion at all about which action to call.

Every question after that is yours:

- They completed an orbit with fourteen frames. Enough, or send them round again?
- Should they flip the object? *Can* they — is it a mug or a wardrobe?
- They say it cannot be flipped. What replaces the second orbit?
- They tapped finish early. Do you refuse, warn, or let them?

Answer all of those properly for a three-orbit flow and you have nineteen distinct prompts and a transition table to match. Almost none of it is 3D. It is about what you are willing to ask a person to do twice.

And now the part worth more than the transition table: **this product ships one orbit.**

Not three. One orbit, and two possible prompts at the end of it — a single *Process* button when there are enough frames, a single *Scan Again* when there are not. No flip, no lower angle, no additional pass.

A dimensional fit for a cover needs the silhouette and the extents. It does not need the underside, and asking a customer mid-purchase to turn a patio heater upside down is not a capture strategy, it is a way to lose a sale.

That is not a wasted machine. It is the reason the flow could be cut to two states by swapping one implementation, without touching the session lifecycle, the frame gate, or a single call site. Building the complicated version is how you find out which parts were product decisions rather than technical ones.

> **Write the flow logic behind a protocol even if you ship the simplest possible version of it.** You cannot tell which branches are product decisions until you have written them all down.

## Reconstruction: fewer choices than you think

The second session is smaller in surface and much larger in what goes wrong.

**The detail level is not a choice.** The API declares preview, reduced, medium, full and raw. On iOS only *reduced* is usable — the higher levels are macOS-only and abort at process time. Model that honestly: an internal type with one case beats a configuration value that silently crashes on a device you already shipped to. When Apple exposes a higher level on iOS, it becomes a new case in a minor version.

**Ask for the bounds, and plan for them not arriving.** You want a model file and a bounding box from the same run. On iOS 17.0 through 17.2 that pairing is intermittently rejected. Your fallback is to load the produced USDZ and read its visual bounds — which has its own iOS 17 problem, because the synchronous model loader is disallowed in async contexts and the async initializer only exists from iOS 18.

The useful move there is not the fallback itself, it is what the result carries. Dimensions should record **which path produced them** and whether they were gravity-aligned. On iOS 17 our fallback deliberately returns a zero box: a detectable failure is worth far more than a confidently wrong measurement flowing into a physical product.

**The output stream does not end.** The session's outputs are an unbounded sequence; "finished" is a value *in* the stream, not the end of it. Iterate it directly and your loop never returns even after reconstruction completes. Wrap it in a small adaptor that terminates on complete, cancelled, or request-error, and the run reads like a run.

Two admissions while we are here, because they are the kind of thing articles usually leave out. First, the outputs that report a rejected or downsampled frame are enumerated and then dropped — the pipeline knows a frame was discarded and the user is never told. "We handle every case" and "we listen to every case" are different claims and only the first is true. Second, the two progress outputs are mutually lossy: one carries a fraction with no stage, the other a stage and an ETA with no meaningful fraction. Feed both into one progress model and the bar visibly resets every time the stage changes. Everyone who has watched this reconstruct has seen it.

**The configuration is a bare default.** Sample ordering, feature sensitivity, object masking — none of them are set. Said plainly rather than dressed up: this is an untuned photogrammetry pipeline that produces good results for this object class, and nobody has yet had a reason to prove a tuned one would be better.

The last one deserves the extra paragraph, because it is the most expensive thing here to have discovered from a crash log.

Nothing in the API suggests cancellation is asynchronous in its effects. It returns, the session reports a terminal state, and every reasonable reading says you may now start another one. Start another one and the crash lands inside RealityKit, on the render thread, with a stack containing none of your code. There is no way to reason your way there from the call site. You get there by noticing the crash only ever happens on a *second* scan, and only when the first one was **cancelled rather than finished**.

That is the general lesson, and it is worth more than the specific fix: when a framework crash has no path through your code, stop looking for the bug and start characterising the conditions. Which scan number. Cancelled or completed. Cold or hot. Those are the variables, and they are the whole fix.

### Two more that look like your bug and are not

**A sensor failure you may retry exactly once.** The capture stack can fail with a sensor error that wraps "media services were reset" — the camera was taken by another client, the media daemon restarted, the device hit a thermal cutoff. Nothing you did causes it and a retry usually works. But only while **no shot exists yet**: the retry reuses the same session and therefore the same images directory, and starting a capture session hard-requires an empty directory. One photo on disk and the retry fails with a different error entirely.

The related decision is stranger and took longer to find. The audio session for capture has its category configured and is **deliberately never activated** — because activating an audio session in the same process that is bringing up ARKit and the camera can itself trigger that same media-services reset. The guard against the failure and one of its causes turned out to be the same subsystem.

**A Metal assertion that only exists under Xcode.** Running one of our targets from Xcode aborted during object detection with a compute-function assertion inside Apple's own shadow shader. It is not a bug in the app: the validating command encoder only exists when Xcode injects the Metal API validation layer, so the assertion cannot fire in a distribution build. The fix is to know that — turn validation off, or launch without the debugger attached — not to go looking for render settings you never set.

## Deciding what leaves the device

Reconstruction gives you a textured USDZ. The texture is genuinely good — real colour, real surface detail, produced entirely on device. Now decide how much of it travels.

Ours does not travel at all. The fitting service wants geometry, so the transfer format carries positions, texture coordinates and triangles, and nothing else. Normals, vertex colours, materials, node transforms, every mesh after the first, and the baked texture image are all dropped.

That is the correct trade for a dimensional fit — the texture is worth megabytes and contributes nothing to a measurement — but it is worth being honest that **the photorealism everyone reacts to in the demo is a local artefact, not an end-to-end one.**

Converting with [Model I/O](https://developer.apple.com/documentation/modelio) is a reader, a flat value type, and a writer. Adding a format means adding a writer. Four things to not miss:

- **The vertex descriptor is an instruction, not documentation.** Hand one to the asset initializer and Model I/O repacks the vertex data into exactly that layout. Get the layout wrong and you get a mesh that reads as noise.
- **`SIMD3<Float>` strides at 16 bytes, not 12.** Three floats are twelve bytes; the type is sixteen-byte aligned. Which is the argument for never hardcoding the number at all — read the stride back from Model I/O when you walk the buffer, and the layout can change without your reader caring.
- **Refuse rather than repair.** Require texture coordinates. Reject non-triangle topology instead of quietly fanning quads into triangles. Assert single-mesh assets out loud rather than silently taking the first one. For a pipeline whose output is a physical product, a loud local failure beats a silent downstream one every time.
- **Widen index types on the way in.** Model I/O will hand you 8-, 16- or 32-bit indices depending on the asset. Normalise once, at the boundary.

### The manifest is where the discipline lives

The mesh goes up with a manifest beside it. This part is cheap to get right on day one and expensive to retrofit.

## Getting the answer back to the page

The transport across a web view is unremarkable: a script injected at document start installs a symmetric API, a message handler receives, and you reply by evaluating JavaScript. The *contract* is the part worth stealing.

<BridgeSequence />

The app requires exactly **one** key on a scan request: which product variant to measure against. Every other key is forwarded to the backend byte-for-byte — same names, same types, nesting intact. Marketing adds an attribute, a category is renamed, a new identifier appears: the web sends it, the backend reads it, and the app never learns what any of it means. It learns only the size limit, and an oversized payload is dropped rather than truncated, because a half-forwarded object is worse than none.

That single decision is why this integration has survived a year of product changes without an app release.

Add a belt to the braces while you are there. If the page never sends its message within a few seconds of finishing its load, read the same identifiers out of the invocation URL's query string and start anyway. The failure this prevents is invisible — a JavaScript error, a cache serving an old bundle, a market where the script is blocked — and all of them produce an app that opens, looks completely healthy, and does nothing.

> **Forward what you do not understand.** A pass-through field costs one line and buys the other team their whole release cycle back.

### A POST that is not idempotent

Submitting a scan creates work. Repeat it and you may create the same work twice, and someone pays for that twice.

Which makes the usual advice — retry on failure, with backoff — wrong here, and wrong in a way that shows up only in production, at scale, as duplicates nobody can reproduce.

Stop treating "did it fail" as one question. It is two: **did the request fail, and is it possible the server did the work anyway?** An error type that answers only the first cannot be retried safely. So every failure carries a three-valued verdict — proven not to have reached the server, might have, or definitely will not succeed on repeat — and the two call sites read it differently. The idempotent poll retries on anything non-terminal. The submit retries only on the first.

<RetryLadder />

The entry people usually get wrong is "connection lost", which is not one failure. If no body byte was ever written, nothing can exist on the other side and a retry is free. If bytes went out, the server may be holding a complete request. Same error, opposite answers — so the transport has to record whether it ever wrote a byte, and the error has to carry that fact with it.

Send an idempotency key from day one even if the backend ignores it today. It costs a header, and it is the thing that collapses this entire problem the moment the server honours it.

And jitter fully: each wait is a fresh random draw between zero and an exponentially growing, capped ceiling. Not the ceiling, and not the ceiling plus noise. A fixed backoff turns a brief server hiccup into a synchronised stampede when every client that failed together returns together.

### The screen is the real deadline

The fit is asynchronous — the submit is acknowledged with an identifier and no measurements, and the client polls until the job finishes. Put your polling budget just *above* the server's own cap on the fit, so in the normal case the timeout is the server's verdict rather than your clock. A longer window only adds silent waiting on a job already declared dead.

But the real ceiling is neither number. This flow also runs on a lightweight, install-free launch surface, which **cannot run background tasks** and has no background transfers. The whole upload and poll must finish while the screen is up. If the user leaves, the transfer stops and no identifier is retained, so the capture is lost rather than resumable.

That reframes every timeout in the system. A generous client budget is not generosity if the platform kills the transfer first. The engineering response is to make the expensive part happen once and finish fast, not to design ever more patient waiting.

Two things follow that survive contact with real users:

**Own long-running work above the screen that started it.** A dismissal is not a cancellation, and users do not know the difference. Anything owned by a view is cancelled by a swipe nobody thought of as a cancel.

**A superseded run must be unable to speak.** Start a second scan while the first is still uploading and, without a guard, the first one's callback lands on the second one's state. Stamp each run with a monotonically increasing generation and check it before writing any state. The same shape of bug shows up in link handling — tap the same product link twice and the value never changes, so nothing fires — and the same fix works: publish a token alongside the value.

> **A timeout on someone else's work is an opinion.** Keep the handle, offer to keep waiting, and never make the expensive part happen twice.

## What this pipeline does not do

Stated plainly, because a pipeline description that only lists wins is marketing.

**The camera intrinsics in the manifest are placeholders.** Plausible, known-good values that match the reference tooling rather than real per-device numbers, because the capture API in use does not surface them. They are labelled as such in the code. If a backend ever does metric reasoning from them, that is a bug waiting with a fuse on it.

**Gravity alignment is asserted, not measured.** The manifest declares an up axis and nothing verifies it. It has been right every time, which is exactly the property that makes it dangerous to keep assuming — and it is one of only two manifest fields the processing engine actually reads.

**The "has LiDAR" flag is not a sensor query.** It is the capture framework's support check under a friendlier name. Correct today, quietly wrong the day Apple supports object capture on something without a depth sensor.

**Reconstruction is untuned**, the progress bar resets on stage changes, and rejected frames are never surfaced to the user.

None of these block the product. All of them are cheap to write down now and expensive to discover later.

## What it added up to

Seven Swift packages, all written in-house, no third-party runtime dependency anywhere in the product. Each is independently shippable and none knows about the others: a capture layer that wraps the platform's 3D stack behind its own value types and does zero networking, a mesh transcoder built as reader → value type → writer, a generic web-view bridge, an async networking layer, a dependency-injection container, a navigation router, and a logger stripped from release builds.

What that bought, concretely:

- A customer measures a real object with a phone and gets a fitted result **inside the web page they were already shopping on** — no app-store detour mid-purchase, and no second product surface to maintain.
- **The web team ships product changes without an iOS release.** One required field, everything else forwarded verbatim.
- **Reconstruction is entirely on device.** No captured frame is uploaded; only a derived mesh, an order of magnitude smaller, with its own hash and a declared coordinate frame.
- **A scan survives the things that actually happen** — a dismissed sheet, a lift with no signal, a device that got hot, a sensor reset, a second scan started on top of the first. None of those lose a capture, and none can create a duplicate job.
- **Every seam is a protocol**, so the capture layer, the transcoder and the bridge each lift into a different product unchanged.

The 3D was the interesting problem. The list above is the product.

## Takeaways

> **Decide which side of the boundary owns the product first.** Every field the app understands is a field the other team cannot change alone.

> **Check every gate up front.** Capture and reconstruction are supported independently, and the one you forgot fails after the user's work cannot be repeated.

> **Own the state machine, and be willing to lie in it.** Showing the camera during initialization is what lets someone aim.

> **Know which of your numbers is authoritative** — a value that only updates on state changes is for display, never for decisions.

> **Write the flow logic behind a protocol even if you ship two states of it.** Building the full version is how you learn which branches were product decisions.

> **Convert framework failures into product prompts** wherever you can. That is most of what a good capture flow is.

> **Refuse before you start rather than fail deep.** Memory, disk and frame count are all cheaper to check than an opaque error three minutes in.

> **When a framework crash has no path through your code, characterise the conditions.** Second scan, cancelled not finished — that was the whole fix.

> **Make failures loud and local.** Mandatory UVs and a hard error on bad topology beat a silently wrong mesh reaching a physical product.

> **Put the coordinate frame and a schema version in the payload before anyone asks.** Three strings and one field, against the most expensive bug class in the domain.

> **"Retry with backoff" is half a policy.** The other half is which requests may be repeated, and it belongs in the error type.

> **Own long-running work above the screen that started it.** A dismissal is not a cancellation.
